1. Objetivo

Implementar un único comportamiento consistente entre Backend y Frontend para el semáforo del diagnóstico inicial, evitando mostrar una conclusión financiera cuando la evidencia todavía es insuficiente.

El semáforo pertenece a la Puerta G5 – Diagnóstico inicial. Para llegar a G5 deben cumplirse previamente las condiciones de carga documental, suficiencia y análisis. El semáforo general no es un indicador aislado y no debe calcularse únicamente a partir de un color recibido desde API.

2. Alcance funcional

  • Validación de estado documental en G2 – Carga documental.
  • Tratamiento del procesamiento documental y sus estados.
  • Separación entre estado funcional y copy visual “Verificado”.
  • Condiciones de habilitación y bloqueo del diagnóstico.
  • Estados permitidos del semáforo general de G5.
  • Reglas de Frontend cuando el API entregue un valor nulo o inconsistente.
  • Guardrails para evitar falsa certeza, rojo por falta de datos o mezcla con severidad S0–S4 de deuda.
Importante: la documentación fuente define reglas funcionales, estados y enums, pero no define el copy visual final. Por ello, “Verificado” puede existir solo como texto de presentación si Producto/UX lo aprueba; no debe crearse como nuevo estado de negocio.

3. Modelo de estados que debe respetar la implementación

3.1 Estado del documento

3.2 Estado del análisis

CampoValores permitidosUso

3.3 Estado del semáforo general

CampoValores permitidosRepresentación

No están definidos como estados funcionales: verified ni null. Ninguno debe incorporarse al enum de negocio del documento o del semáforo.

4. Reglas de G2 — Carga documental

La Puerta G2 se supera únicamente cuando existe al menos un documento con document_upload_status = usable.

uploadedAÚN NOMostrar archivo cargado y estado de procesamiento.“Cargado” no equivale a usable.
usableSÍPermitir avanzar a revisión/suficiencia.Es el único estado que satisface por sí mismo la condición documental de G2.
non_processableNOInformar que debe subir/revisar otro archivo.Bloquea avance.
outdatedNOSolicitar documento vigente.No debe tratarse como base suficiente.
duplicateNONo generar una nueva base válida por duplicidad.Debe conservarse trazabilidad del evento.

4.1 Regla específica para “Verificado”

RN-G2-VER-01. El Frontend no debe generar ni persistir un estado funcional verified. Si la interfaz muestra la palabra “Verificado”, ésta será únicamente un label visual y deberá corresponder a un estado funcional existente.

5. Reglas de procesamiento documental — G4

01

queued

Documento recibido y pendiente de iniciar análisis. No hay diagnóstico ni semáforo.

02

in_progress

Análisis en ejecución. Mostrar progreso; no concluir estado financiero.

03

delayed_soft / delayed_long

Demora controlada. Mantener avance y ofrecer salida segura.

completed / failed

Completed habilita evaluación de suficiencia. Failed debe llevar a recuperación, no a semáforo.

6. Reglas del Semáforo General — Puerta G5

La Puerta G5 se considera funcionalmente resuelta cuando el sistema tiene definidos semáforo, presión principal y CTA dominante. El semáforo representa una lectura inicial de salud financiera del mes y no debe copiar la escala S0–S4 de deuda.

Valor BackendEstado visualCondición funcionalRegla / CTA
in_control VERDE · En control Base documental suficiente, indicadores críticos disponibles y sin presión principal crítica. Puede existir una oportunidad menor de optimización. Optimizar pagos recurrentes o avanzar a Mi Perfil Financiero.
attention AMARILLO · Atención Base usable, con datos no bloqueantes por confirmar, movimientos pendientes, fugas detectadas, pagos recurrentes relevantes o margen ajustado sin evidencia crítica. Completar/revisar señal principal o continuar a Perfil con advertencia.
risk ROJO · Riesgo Existe base usable y evidencia suficiente de presión relevante: sobrecarga, compromisos altos, gastos/recurrentes que presionan la estabilidad u otra señal fuerte. Atender riesgo principal o revisar acción sugerida antes de continuar.
no_diagnosis SIN DIAGNÓSTICO Falta documento usable, ingreso principal, movimientos recientes, base mínima de compromisos/pagos; hay documento no procesable o confianza insuficiente. Completar información clave, corregir o cargar documento usable.

6.1 Guardrails obligatorios

  1. No mostrar rojo por falta de información. La ausencia de datos debe resolverse como no_diagnosis o bloqueo.
  2. No diagnosticar sin documento usable ni sin los datos críticos mínimos.
  3. No copiar S0–S4 de deuda al semáforo general del onboarding inicial.
  4. Los datos inferidos, manuales o por confirmar deben afectar confianza y/o advertencia; no deben presentarse como certeza.
  5. Debe existir una única presión principal y una única acción/CTA dominante por evaluación.
  6. La ruta manual/texto/voz solo complementa después de carga documental válida; no sustituye G2.

7. Tratamiento requerido cuando API entregue light: null

Brecha de contrato identificada: la documentación no define null como un estado del semáforo. El enum funcional contempla in_control, attention, risk y no_diagnosis.

7.1 Regla propuesta de implementación

EscenarioTratamiento obligatorio
Usuario aún no llega a G5 o el análisis está queued/in_progress/delayed_* El Front no debe renderizar un semáforo final. Mostrar estado de proceso correspondiente. null puede existir transitoriamente en transporte, pero no representa un color ni una evaluación.
G5 intenta mostrarse y el backend retorna light: null No asignar verde/amarillo/rojo por defecto. Validar los campos de suficiencia/modo. Si éstos indican bloqueo o falta real de datos, presentar Sin diagnóstico. Si los campos son contradictorios, tratar como inconsistencia de contrato y registrar error.
Backend ya determinó falta de base o datos insuficientes El contrato objetivo debe responder general_traffic_light_status = "no_diagnosis", no null.
light: null con diagnóstico marcado como completo Inconsistencia técnica. No inventar color en Front. Registrar/telemetría y usar fallback seguro sin falsa certeza. 
// Pseudológica Frontend propuesta
if (currentGate !== "G5_diagnostico" || analysisStatus !== "completed") {
  hideFinalTrafficLight();
  renderProcessState();
} else if (trafficLightStatus == null) {
  if (diagnosticMode === "blocked" ||
      diagnosticMode === "not_available" ||
      ["datos_clave_insuficientes","sin_base","documento_no_procesable"].includes(sufficiencyStatus)) {
    renderNoDiagnosis();
  } else {
    renderSafeFallback();
    logContractInconsistency("TRAFFIC_LIGHT_NULL_AT_G5");
  }
} else {
  renderTrafficLight(trafficLightStatus);
}

8. Requerimientos específicos de Frontend

IDRequerimiento
RF-FE-01No crear un enum local verified para el estado documental.
RF-FE-02Usar document_upload_status como fuente del estado funcional del documento.
RF-FE-03Usar analysis_status para representar progreso, demora, término o falla del análisis.
RF-FE-04No mostrar un color de semáforo final mientras G4 no haya terminado y G5 no tenga evaluación válida.
RF-FE-05Renderizar exclusivamente los cuatro estados permitidos de general_traffic_light_status.
RF-FE-06No interpretar null como verde, amarillo o rojo.
RF-FE-07Cuando falte información crítica, mostrar “Sin diagnóstico” o el estado de bloqueo correspondiente.
RF-FE-08Si se mantiene el copy “Verificado”, debe ser solo visual y estar asociado a una combinación funcional válida; no persistirlo ni enviarlo como estado a Backend.
RF-FE-09Ante estados contradictorios, utilizar fallback seguro y registrar trazabilidad técnica.
RF-FE-10La navegación desde G5 debe respetar la acción dominante definida por la evaluación.

9. Contrato mínimo esperado Frontend ↔ Backend

El nombre real de los campos puede adaptarse al contrato técnico vigente, pero debe conservar la equivalencia funcional.

{
  "current_gate": "G5_diagnostico",
  "document": {
    "document_upload_status": "usable"
  },
  "analysis": {
    "analysis_status": "completed"
  },
  "diagnostic": {
    "sufficiency_status": "base_suficiente",
    "diagnostic_mode": "complete",
    "diagnostic_status": "completed",
    "general_traffic_light_status": "in_control",
    "dominant_pressure_code": "no_pressure",
    "dominant_cta_code": "ver_perfil",
    "confidence_level": "high",
    "rule_version": "onboarding_diagnosis_v1_0"
  }
}

Contrato objetivo: cuando el diagnóstico no pueda determinarse por falta de datos, el backend debe informar explícitamente general_traffic_light_status = "no_diagnosis" junto con el motivo de bloqueo/suficiencia, evitando utilizar null como resultado funcional final.

10. Criterios de aceptación

IDCriterio de aceptación
CA-01Dado un documento con estado uploaded, el usuario no supera G2 hasta que exista al menos un documento usable.
CA-02Dado un documento non_processable, el flujo bloquea avance y solicita corrección o nueva carga.
CA-03El sistema no utiliza verified como estado funcional de documento ni de análisis.
CA-04El término exitoso del análisis se representa con analysis_status = completed.
CA-05La aptitud documental se representa con document_upload_status = usable.
CA-06El semáforo solo puede tomar in_control, attention, risk o no_diagnosis.
CA-07Falta de documento usable o datos críticos nunca produce estado rojo por defecto.
CA-08Rojo/Riesgo requiere evidencia suficiente y una presión principal identificada.
CA-09Amarillo/Atención admite datos por confirmar únicamente cuando éstos no son bloqueantes.
CA-10Verde/En control requiere base suficiente y ausencia de presión principal crítica.
CA-11Si el API retorna light: null en G5, el Front no inventa un color y ejecuta el fallback seguro definido.
CA-12Cuando la falta de información es una condición válida de negocio, Backend normaliza el resultado a no_diagnosis.
CA-13Los estados de demora de análisis no generan diagnóstico ni color final.
CA-14La severidad S0–S4 de deuda no reemplaza el semáforo general del onboarding inicial.
CA-15Cada evaluación conserva versión de regla, presión principal y CTA dominante para trazabilidad.

12. Decisión de implementación resumida

Regla principal para desarrollo:
G2 valida que exista al menos un documento usable. G4 controla el procesamiento mediante analysis_status. G5 calcula y muestra el semáforo únicamente con un diagnóstico válido. “Verificado” no es un estado funcional y light: null no es un resultado válido del semáforo final. Si falta evidencia, el resultado de negocio debe ser no_diagnosis, nunca un color inferido por el Front.
