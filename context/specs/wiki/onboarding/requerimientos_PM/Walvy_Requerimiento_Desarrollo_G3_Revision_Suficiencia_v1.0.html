Requerimiento de Desarrollo — Puerta G3: Revisión y Suficiencia

Especificación funcional y técnica para calcular la suficiencia de los datos detectados, permitir o bloquear el diagnóstico y controlar los estados/CTAs de la revisión documental.
PuertaG3 — Revisión y suficiencia
Versión1.0
Fecha23-08-2026
DestinatarioDesarrollo / QA

1. Objetivo

Implementar la Puerta G3 como una evaluación de suficiencia y no solamente como una pantalla de revisión. Al ingresar a G3 el sistema ya debe disponer de una carga documental usable y de los indicadores extraídos; G3 determina si la información habilita un diagnóstico completo, un diagnóstico parcial controlado o si debe bloquearse el avance.

Regla central: G3 avanza hacia análisis cuando existe Base suficiente o cuando existe Datos por confirmar y la condición permite diagnóstico parcial. Los datos clave insuficientes bloquean el diagnóstico y obligan a completar/corregir información.

2. Definición de la puerta G3

EntradaSistema detecta indicadores desde documento(s) cargado(s).
Condición de avanceBase suficiente o datos por confirmar no bloqueantes.
BloqueoDatos clave insuficientes o confianza global insuficiente.
SalidaAnálisis (G4) o completar información clave.
GuardrailNo mostrar diagnóstico como certeza si falta evidencia crítica.

4. Estados de cada indicador

Estado funcionalDefiniciónEfecto en G3Valor técnico sugerido/documentado

Por confirmarEl dato aparece, pero requiere confirmación, categorización o corrección puntual.Puede permitir diagnóstico parcial si no es bloqueante.por_confirmar
No detectadoDato inexistente o no utilizable.Bloquea si corresponde a un requisito mínimo crítico.no_detectado
DesactualizadoDato fuera del período o sin vigencia suficiente.Reduce confianza y exige corrección cuando afecte lectura.desactualizado

No inventar estado técnico “Verificado”. Los estados funcionales documentados para el indicador son los anteriores. Si UX desea mostrar una etiqueta visible “Verificado”, esta debe ser solamente un label de presentación mapeado a un estado soportado (por ejemplo, dato detectado/confirmado) y no un nuevo valor de persistencia sin definición de Producto/BDD.

6. Reglas funcionales obligatorias

REQ-G3-001
Evaluación automática. Al ingresar a G3 el backend debe evaluar y persistir la suficiencia a partir de los indicadores detectados y su confianza.
REQ-G3-002
Base suficiente. Debe cumplirse documento usable + ingreso + movimientos recientes + al menos compromisos base o pagos recurrentes + confianza global suficiente.
REQ-G3-003
Diagnóstico parcial controlado. Solo puede habilitarse con base documental usable y faltantes no bloqueantes; se debe comunicar menor precisión.
REQ-G3-004
Máximo un crítico no detectado para evaluar parcialidad. Si existen varios críticos no detectados, el diagnóstico debe quedar bloqueado.
REQ-G3-005
Dato crítico por confirmar. Si su confirmación puede cambiar la lectura central, no se permite diagnóstico parcial.
REQ-G3-006
Instrumentos de pago. Su ausencia no bloquea por sí sola el diagnóstico cuando existe la base mínima restante.
REQ-G3-007
Carga útil pero insuficiente ≠ error. Debe tratarse como avance incompleto y orientar al usuario a completar evidencia, no como fallo técnico.
REQ-G3-008
Insuficiencia no es riesgo. La falta de datos no puede producir estado financiero rojo. La salida posterior será “Sin diagnóstico” o bloqueo.
REQ-G3-009
CTA dominante único. El estado G3 debe determinar un CTA principal. Los secundarios deben permanecer subordinados.
REQ-G3-010
Recalcular tras corrección. Cada confirmación/corrección que afecte un indicador crítico debe volver a evaluar sufficiency_status, diagnostic_mode y CTAs.
REQ-G3-011
Manual/texto/voz. Solo se habilita después de una carga documental válida y para completar/corregir indicadores puntuales; no puede reemplazar la carga inicial.
REQ-G3-012
Trazabilidad. Toda modificación debe conservar origen, indicador afectado, documento/evidencia, confianza, confirmación del usuario y versión de regla.
REQ-G3-013
No salto de puerta. Ningún estado bloqueado de G3 puede navegar a G4 mediante manipulación de frontend; el backend debe validar la condición.
REQ-G3-014
Persistencia y retoma. Si el usuario sale mientras completa información, la aplicación debe conservar el estado y retomar en el punto pendiente de mayor valor.

9. Reglas de frontend

  • El frontend no decide por sí solo si el usuario puede iniciar G4; debe consumir el resultado de suficiencia del backend.
  • Mostrar el resumen de indicadores detectados y señalar cuáles requieren confirmación/corrección.
  • Con base_suficiente, el CTA principal es Comenzar diagnóstico. No solicitar información extra innecesaria.
  • Con datos_por_confirmar no bloqueantes, el CTA principal es Completar información clave; “Comenzar diagnóstico con esta base” solo aparece si partial_diagnostic_allowed=true.
  • Con dato crítico por confirmar o datos clave insuficientes, no mostrar ninguna acción que inicie diagnóstico.
  • Una carga insuficiente debe presentarse como un estado funcional de completitud, no como error técnico.
  • Datos inferidos/manuales/asistidos deben diferenciarse visualmente cuando corresponda y nunca mostrarse con certeza equivalente a dato documental confirmado.
  • Al confirmar/corregir un dato, refrescar el resultado de suficiencia recibido desde backend y actualizar CTAs sin reiniciar el flujo.

10. Regla de backend — pseudocódigo de referencia

evaluateG3(context):

  if no_document_uploaded:
      sufficiency_status = "sin_base"
      diagnostic_mode = "not_available"
      partial_diagnostic_allowed = false
      dominant_cta_code = "cargar"
      return

  if document_not_processable:
      sufficiency_status = "documento_no_procesable"
      diagnostic_mode = "not_available"
      partial_diagnostic_allowed = false
      blocking_reason = "documento_no_procesable"
      return

  if confidence_level == "insufficient":
      block("datos_clave_insuficientes", "confianza_insuficiente")
      return

  if main_income_missing:
      block("datos_clave_insuficientes", "ingreso_faltante")
      return

  if recent_movements_missing:
      block("datos_clave_insuficientes", "movimientos_faltantes")
      return

  if neither(base_commitments_available, recurring_payments_available):
      block("datos_clave_insuficientes", "pagos_compromisos_insuficientes")
      return

  if main_income_confirmed
     and recent_movements_confirmed
     and (base_commitments_confirmed or recurring_payments_confirmed)
     and confidence_level in ["high", "medium"]:

      sufficiency_status = "base_suficiente"
      diagnostic_mode = "complete"
      partial_diagnostic_allowed = false
      dominant_cta_code = "comenzar"
      return

  # Existe base, pero quedan elementos por confirmar.
  sufficiency_status = "datos_por_confirmar"
  dominant_cta_code = "completar"

  if pending_critical_can_change_central_reading:
      diagnostic_mode = "blocked"
      partial_diagnostic_allowed = false
      secondary_cta_codes = ["continuar_mas_tarde"]
      return

  if critical_not_detected_count <= 1
     and missing_items_are_non_blocking
     and minimum_basis_is_interpretable:

      diagnostic_mode = "partial"
      partial_diagnostic_allowed = true
      secondary_cta_codes = ["comenzar_con_base"]
      warning_reason = "datos_por_confirmar"
      return

  block("datos_clave_insuficientes", calculated_blocking_reason)
El pseudocódigo expresa la regla funcional. No debe utilizarse para introducir umbrales o equivalencias no documentadas. La decisión “puede cambiar la lectura central” debe quedar encapsulada/versionada en la capa de reglas y ser trazable.

13. Controles técnicos mínimos

  • Backend como autoridad: permisos de avance y bloqueo validados en API.
  • Idempotencia: reevaluar G3 varias veces con la misma evidencia no debe crear evaluaciones inconsistentes ni duplicadas.
  • Concurrencia: evitar que dos confirmaciones simultáneas dejen estados contradictorios.
  • Auditoría: registrar evaluación, regla/version, momento, resultado y razón de bloqueo sin exponer datos financieros sensibles en logs.
  • Persistencia: mantener el avance para retoma; la navegación o cierre de la app no debe perder la evaluación vigente.
  • Contrato FE/BE: enums compartidos/versionados; no duplicar reglas de suficiencia en frontend con lógica independiente.

14. Fuera de alcance / no asumir

  • No crear nuevos estados de suficiencia, indicador o CTA fuera de los catálogos documentados sin decisión formal.
  • No permitir que voz/texto/formulario reemplacen la carga documental inicial.
  • No tratar un dato inferido o manual como equivalente a evidencia documental confirmada.
  • No convertir falta de información en “riesgo” financiero.
  • No hardcodear una decisión nueva sobre qué faltante “cambia la lectura central” sin regla versionada.
  • No iniciar G4 por decisión exclusiva del frontend.

15. Definición de terminado (DoD)

La implementación de G3 se considera terminada cuando:

  • están implementados los cinco valores documentados de sufficiency_status;
  • el modo completo/parcial/bloqueado responde a las reglas anteriores;
  • partial_diagnostic_allowed gobierna efectivamente el CTA “Comenzar diagnóstico con esta base”;
  • cada bloqueo contiene una razón trazable;
  • el frontend no mantiene lógica paralela contradictoria;
  • se reevalúa el estado después de confirmar/corregir datos;
  • se conserva el avance al abandonar/retomar;
  • los CA-01 a CA-14 cuentan con evidencia QA positiva/negativa/alternativa según corresponda.
