M1 – Implementación Semáforo de Diagnóstico Onboarding – Puerta G5

Requerimiento funcional y técnico para Backend, Frontend y QA.

Módulo: M1 Onboarding Puerta: G5 – Diagnóstico Tipo: Requerimiento de Desarrollo Versión: 1.0

1. Objetivo

Implementar la lógica de evaluación y respuesta del semáforo general del diagnóstico inicial del Onboarding, correspondiente a la Puerta G5 – Diagnóstico, de manera que el usuario obtenga un estado coherente con la suficiencia y calidad de la información disponible.

En control in_control

La información permite una lectura suficiente y no existen señales de presión crítica.

Atención attention

Existe información usable, pero hay señales que requieren revisión.

Riesgo risk

Existe evidencia suficiente de una presión financiera relevante.

Sin diagnóstico no_diagnosis

No existe información suficiente o confiable para emitir un diagnóstico.

Campo funcional definido:

general_traffic_light_status

Valores permitidos:

in_control | attention | risk | no_diagnosis

3. Regla de suficiencia previa al semáforo

3.1 Base suficiente

Se considera base suficiente cuando:

  • Existe un documento usable.
  • El ingreso principal está detectado o confirmado.
  • Los movimientos recientes están detectados o confirmados.
  • Existe al menos información de compromisos base o pagos recurrentes detectados/confirmados.
  • La confianza global es high o medium.
  • No existe un bloqueo funcional que impida generar el diagnóstico.
diagnostic_mode = complete

3.2 Datos por confirmar

Cuando existe documento usable y la lectura central puede realizarse, pero existen datos no críticos pendientes de confirmación: 

diagnostic_mode = partial

Solo podrá generarse diagnóstico parcial cuando:

partial_diagnostic_allowed = true

Debe existir además una advertencia mediante:

diagnostic_warning_reason
Los datos pendientes no deben transformarse automáticamente en Riesgo.

3.3 Base insuficiente

Si falta información crítica o la confianza es insuficiente:

diagnostic_mode = blocked | not_available
general_traffic_light_status = no_diagnosis
diagnostic_blocking_reason = <motivo>
diagnosis_basis_note_variant = insufficient_basis

4. Regla del semáforo – En control

general_traffic_light_status = in_control

Asignar cuando exista una base suficiente para diagnóstico y no exista evidencia de una presión financiera relevante.

general_traffic_light_status = risk

8. Tratamiento obligatorio de light = null

Una vez ejecutada y resuelta la evaluación G5, la respuesta no debe entregar "light": null.

Si el campo técnico utilizado por la API es light, deberá mapearse al campo funcional:

general_traffic_light_status

Una vez ejecutada G5, light solo podrá contener:

in_control | attention | risk | no_diagnosis

Regla de fallback

Si el motor no puede determinar Verde, Amarillo o Rojo debido a falta de información, deberá devolver:

light = no_diagnosis

y no:

light = null

El resultado deberá acompañarse de:

diagnostic_blocking_reason
La documentación funcional no define qué valor debe tener light antes de que exista una evaluación G5. Por lo tanto, esta regla aplica a respuestas donde el diagnóstico G5 haya sido ejecutado o resuelto.

9. Presión dominante

Cada evaluación debe contener una única presión dominante.

dominant_pressure_code

Valores documentados:

overload
margin_compromised
recurring_payments
high_commitments
pending_movements
leaks_detected
data_to_confirm
optimization
monthly_focus
no_pressure

Si existen múltiples señales simultáneamente, el motor deberá seleccionar una única presión dominante conforme a las reglas/prioridades configuradas.

10. CTA dominante

Cada evaluación debe generar una única acción principal.

Tipos de acción documentados:

optimize_recurring_payments
review_pending_movements
review_detected_leaks
address_overload_risk
review_commitments
complete_key_information
view_financial_profile

Códigos de CTA disponibles:

cargar
completar
comenzar
comenzar_con_base
revisar
esperar
avisarme
ver_perfil
Los CTA secundarios podrán existir, pero no deberán competir visual o funcionalmente con la acción dominante.

14. Criterios de aceptación

IDCriterio
CA01Dado que se ejecuta G5, el resultado deberá contener exclusivamente in_control, attention, risk o no_diagnosis.
CA02Dado que G5 fue evaluada, light/general_traffic_light_status no deberá retornar null.
CA03Si falta un indicador crítico o la confianza es insuficiente, el resultado debe ser no_diagnosis y deberá informarse diagnostic_blocking_reason.
CA04La falta de datos no puede generar por sí sola el estado risk.
CA05Con base suficiente y sin presión crítica, el resultado podrá ser in_control.
CA06Con base usable y señales no críticas que requieren revisión, el resultado debe ser attention.
CA07Solo con evidencia suficiente de presión relevante el resultado podrá ser risk.
CA08Si existen múltiples señales simultáneas, solo una deberá quedar como dominant_pressure_code.
CA09Cada diagnóstico deberá exponer una única acción dominante.
CA10Cada evaluación deberá persistir rule_version y evaluated_at.
CA11Frontend deberá representar el estado recibido sin reinterpretar la lógica financiera.
CA12Al retomar el onboarding debe recuperarse o recalcularse la evaluación según la regla de versionamiento definida.

16. Fuera de este requerimiento / definiciones pendientes

La documentación disponible no define umbrales numéricos cerrados para determinar cuándo un margen pasa de adjusted a pressured, cuándo un compromiso debe considerarse high o cuál es la prioridad exacta entre todas las presiones simultáneas.

Estos valores no deben inventarse ni quedar hardcodeados sin definición de Producto. Los parámetros y prioridades que gobiernen el cálculo deberán quedar configurables/versionados mediante la lógica de rule_parameter y deberán ser aprobados antes de cerrar la implementación definitiva del motor.

17. Definition of Done

  • Backend implementa y persiste la evaluación del semáforo.
  • La API entrega uno de los cuatro estados válidos al finalizar G5.
  • No se retorna null para el semáforo cuando G5 ya fue evaluada.
  • Frontend representa correctamente el resultado recibido.
  • Se mantiene una única presión dominante.
  • Se mantiene un único CTA dominante.
  • Se registra trazabilidad de la evaluación.
  • QA ejecuta satisfactoriamente escenarios En control, Atención, Riesgo y Sin diagnóstico.
